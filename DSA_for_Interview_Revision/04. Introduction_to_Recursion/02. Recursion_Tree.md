# Recursion Tree — Complete Deep Dive

---

## 1. What is a Recursion Tree?

A recursion tree is a diagram that shows **every single function call** made during a recursive run, drawn as a tree:

- Each **node** = one function call (with its specific input, e.g. `factorial(3)`)
- Each **child** of a node = a recursive call made *from inside* that call
- Each **leaf** (bottom-most node, no children) = a call that hit the **base case** and returned directly without calling itself again

Drawing this out by hand is the single best habit for actually understanding recursion — it turns an abstract idea ("the function calls itself") into a picture you can trace with your finger.

---

## 2. Type 1: Linear Recursion Tree (factorial — one call per level)

Some recursive functions only call themselves **once** per call. This creates a tree that's really just a straight line — one child per node, going down.

```java
int factorial(int n) {
    if (n == 0) return 1;
    return n * factorial(n - 1);
}
```

**The tree for factorial(4):**
```
factorial(4)
     |
factorial(3)
     |
factorial(2)
     |
factorial(1)
     |
factorial(0)   ← base case, returns 1 (this is the only leaf)
```

**How it works, step by step:**

1. **Going down (the "calling" phase):** Each call immediately makes another call before it can do anything else. `factorial(4)` calls `factorial(3)`, which calls `factorial(2)`, and so on. Every one of these calls is now sitting on the call stack, **paused**, waiting.
2. **Hitting the bottom:** `factorial(0)` is the base case. It doesn't call anyone else — it just returns `1` immediately. This is the only leaf in this tree.
3. **Going back up (the "returning"/"unwinding" phase):** Now that `factorial(0)` has answered, `factorial(1)` (which was paused waiting for it) can finish: `1 * 1 = 1`. It returns that to `factorial(2)`, which finishes: `2 * 1 = 2`. This continues all the way back up to `factorial(4)`, which finishes: `4 * 6 = 24`.

**Key insight:** because there's only one child per node, this tree has a **depth of n+1** (5 levels for n=4) and does exactly **n+1 total function calls** — nothing is repeated, nothing branches.

---

## 3. Type 2: Branching Recursion Tree (Fibonacci — two calls per level)

Some recursive functions call themselves **more than once** in a single call. This creates a tree that actually branches out, like a real tree.

```java
int fibonacci(int n) {
    if (n <= 1) return n;
    return fibonacci(n - 1) + fibonacci(n - 2);
}
```

**The tree for fibonacci(4):**
```
                    fib(4)
                  /        \
             fib(3)          fib(2)
            /      \         /      \
        fib(2)   fib(1)   fib(1)   fib(0)
       /     \
   fib(1)   fib(0)
```

**How to read this tree:**
- `fib(4)` needs BOTH `fib(3)` and `fib(2)` to finish before it can add their results together
- `fib(3)` itself needs BOTH `fib(2)` and `fib(1)` to finish first
- This keeps branching until you hit the base cases: `fib(1)` returns `1` and `fib(0)` returns `0` — these are the leaves

**The big "aha" most people miss:** look closely — `fib(2)` appears **twice** in this tree (once under `fib(3)`, once directly under `fib(4)`), and `fib(1)` appears **three times**. The function is recalculating the exact same values over and over, from scratch, every single time, because plain recursion has no memory of what it already computed.

**Why this matters:** for small numbers like `fib(4)`, this waste barely matters. But for something like `fib(40)`, the tree becomes enormous — millions of repeated calls — making plain recursive Fibonacci extremely slow (exponential time complexity). This exact problem is what **memoization** and **dynamic programming** are built to fix (you'll cover this properly in Phase 12) — by storing each answer the first time it's computed, so repeated branches just look it up instead of recalculating.

---

## 4. Type 3: Multi-Branch Recursion Tree (e.g. generating subsets/combinations)

Some recursive functions branch even more — 3, 4, or more calls per node — common in backtracking problems you'll meet in Phase 5. The same rules apply, just with more children per node. Example shape for a 3-way branch:

```
              solve(n)
          /      |      \
     path A   path B   path C
      / \       ...      ...
   ...   ...
```

You don't need to memorize this type yet — just recognize that **however many recursive calls happen inside one function call, that's how many children that node has** in the tree. One call → straight line. Two calls → binary branching (like Fibonacci). Three+ calls → wider branching (used in backtracking).

---

## 5. How to Draw a Recursion Tree Yourself (Step-by-Step Method)

1. Write the very first call at the top (or write it as the root, your choice — many people find writing the first call at the top and branches going down easiest, like a family tree)
2. Look inside the function: how many recursive calls does it make? That's how many lines/branches come out of this node.
3. Write each recursive call as a child node, with its actual input value (not just "recursive call" — write `fib(2)`, not just a blank box)
4. Repeat this same process for every new node you just added
5. Stop branching a node the moment its input satisfies the base case — mark that node as a leaf (many people circle leaves or use a different color)
6. Once the whole tree is drawn, work from the leaves back up: fill in what each node actually returns, based on its children's returned values

**Tip:** for a function with two recursive calls, if you're doing this on paper, draw the tree top-down like a family tree — it naturally spreads out and stays readable. For a linear (one-call) recursion, it's fine to just draw it as a straight vertical or horizontal list.

---

## 6. Why the Recursion Tree Matters for Interviews

- It's the fastest way to **count total function calls**, which is exactly how you figure out time complexity of a recursive solution (e.g. Fibonacci's tree roughly doubles in size per level, which is a big clue that it's exponential time).
- It visually exposes **repeated work** (like `fib(2)` showing up multiple times), which is exactly the insight that leads to memoization/DP as an optimization.
- Interviewers frequently ask you to **draw the recursion tree on a whiteboard** for a given function — being fast and comfortable at this is a genuinely high-value skill, not just theory.

## 7. Full Interview Q&A

**Q1: What does each node in a recursion tree represent?**
A: One specific function call, with its specific input value.

**Q2: What determines how many children a node has in a recursion tree?**
A: The number of recursive calls made inside that function call. One recursive call → one child (linear tree). Two recursive calls → two children (branching tree), and so on.

**Q3: What is a leaf in a recursion tree?**
A: A call that hit the base case — it returned a value directly without making any further recursive calls.

**Q4: Why does Fibonacci's recursion tree recompute the same values multiple times?**
A: Because plain recursion has no memory — every recursive call recalculates its answer from scratch, even if an identical call (same input) was already computed elsewhere in the tree.

**Q5: How is a recursion tree useful for figuring out time complexity?**
A: The total number of nodes in the tree equals the total number of function calls made — counting or estimating that (e.g. noticing the tree doubles in size each level, like in Fibonacci) tells you the growth rate/time complexity of the algorithm.

**Q6: What's the difference between the recursion tree for factorial and for Fibonacci?**
A: Factorial's tree is linear — one child per node, forming a straight line down to a single base case. Fibonacci's tree branches — two children per node, forming a spreading tree with multiple (and repeated) base case calls.

**Q7: How does a recursion tree relate to memoization?**
A: A recursion tree often reveals identical subproblems appearing in multiple places (like repeated `fib(2)` calls). Memoization stores the answer to each unique subproblem the first time it's computed, so any repeated node in the tree can just be looked up instantly instead of recalculated.

---

## 8. One-Minute Summary (say this out loud before an interview)

"A recursion tree shows every function call as a node, with children representing the recursive calls made inside it, and leaves representing calls that hit the base case. Linear recursion like factorial produces a straight-line tree with no repeated work. Branching recursion like Fibonacci produces a spreading tree that often recomputes identical subproblems multiple times — which is exactly the inefficiency that memoization and dynamic programming are designed to eliminate."
