# Recursion — Complete Interview Prep Notes

---

## 1. What is Recursion? (Simplest Explanation)

Recursion is when a **function calls itself** to solve a smaller version of the same problem, until it reaches a point simple enough to answer directly.

Think of it like Russian nesting dolls — you open one doll to find a smaller doll inside, open that to find an even smaller one, and so on... until you reach the smallest doll that doesn't open any further. That smallest doll is your **base case**.

Every recursive function needs exactly two parts:
1. **Base Case** — the condition where the function stops calling itself and just returns a direct answer
2. **Recursive Case** — where the function calls itself again, but with a smaller/simpler input, moving closer to the base case

If you forget the base case (or write it wrong), the function calls itself forever — this causes a **StackOverflowError**, explained in detail below.

---

## 2. How Function Calls Actually Work (The Call Stack)

Every time you call a function — recursive or not — Java doesn't just "run the code and forget about it." It stores information about that call in a special memory area called the **Call Stack**.

Think of the call stack like a **stack of plates**:
- Each time a function is called, a new plate (called a **stack frame**) is placed on top
- That plate holds that function call's local variables and its "return address" (where to continue once it finishes)
- When a function finishes and returns a value, its plate is removed from the top
- The function below it (the one that called it) resumes exactly where it left off, now using the returned value

**This is exactly why recursion works** — every recursive call gets its own separate plate/frame, with its own separate copy of variables and parameters. They don't overwrite each other.

## 3. Recursion Trace Example: factorial(4)

```java
int factorial(int n) {
    if (n == 0) return 1;        // base case
    return n * factorial(n - 1); // recursive case
}
```

**Going down (calls stack up, nothing is calculated yet):**
```
factorial(4)
  → factorial(3)
      → factorial(2)
          → factorial(1)
              → factorial(0) → returns 1   ← base case hit, stack starts unwinding
```

**Coming back up (each call waits for the one below it to finish, then multiplies):**
```
factorial(1) = 1 * factorial(0) = 1 * 1 = 1
factorial(2) = 2 * factorial(1) = 2 * 1 = 2
factorial(3) = 3 * factorial(2) = 3 * 2 = 6
factorial(4) = 4 * factorial(3) = 4 * 6 = 24
```

**This "waiting" part is the single most important thing to understand:** `factorial(4)` cannot finish its multiplication until `factorial(3)` gives it an answer. And `factorial(3)` can't finish until `factorial(2)` answers. This chain of "waiting for the next one to resolve" is exactly what the call stack is managing — each call is paused, sitting on the stack, until the call it made underneath it returns a value.

## 4. What is Stack Overflow? (The Concept Kunal Emphasizes)

Every stack frame takes up a small amount of memory. If a recursive function keeps calling itself without ever reaching its base case (or the base case is written incorrectly), stack frames keep piling up — call after call after call — until the memory reserved for the call stack completely fills up.

When that happens, Java throws a **`StackOverflowError`**.

```java
// BAD — missing/broken base case
int badFunction(int n) {
    return n * badFunction(n - 1);  // never checks for a stopping point!
}
```
This keeps calling itself forever (well, until the stack runs out of memory) because there's no base case telling it when to stop.

**Common causes of stack overflow in recursion:**
- No base case at all
- Base case exists but is never actually reached (e.g., wrong condition, or the recursive call doesn't move toward the base case)
- Base case is correct, but the input is so large that even a correct recursion runs out of stack space (this happens with very deep recursion — thousands of nested calls)

**Simple rule to avoid this:** always ask two questions when writing a recursive function —
1. "What is the simplest case where I can return an answer directly, without recursing further?"
2. "Does every recursive call move closer to that simplest case?"

If the answer to both is yes, you're safe from infinite recursion.

## 5. Why Each Function "Waits" — The Core Intuition

This is the part that makes recursion click for most people. When `factorial(4)` calls `factorial(3)`, execution doesn't move on to the next line — `factorial(4)` is **paused and waiting**, sitting on the call stack, doing nothing until `factorial(3)` completely finishes and returns its answer.

This waiting happens at every level:
- `factorial(4)` waits for `factorial(3)`
- `factorial(3)` waits for `factorial(2)`
- `factorial(2)` waits for `factorial(1)`
- `factorial(1)` waits for `factorial(0)`
- `factorial(0)` is the base case — it doesn't wait for anyone, it just returns `1` immediately

Once `factorial(0)` returns, all those paused calls "wake up" one at a time, from the bottom up, each one finishing its multiplication and returning its own answer to the call above it.

**This is exactly why recursion uses more memory than a simple loop** — every one of those "waiting" calls is still sitting in memory on the call stack, holding its place, until it's resolved.

## 6. Fibonacci — Second Core Example

```java
int fibonacci(int n) {
    if (n <= 1) return n;                       // base case
    return fibonacci(n - 1) + fibonacci(n - 2);  // recursive case
}
```

Unlike factorial, Fibonacci makes **two recursive calls** at each step, not one. This creates a branching tree of calls instead of a single line:

```
                fib(4)
              /        \
         fib(3)          fib(2)
        /      \         /      \
    fib(2)   fib(1)   fib(1)   fib(0)
   /     \
fib(1)  fib(0)
```

**Key insight:** notice `fib(2)` gets calculated more than once here — this repeated work is why plain recursive Fibonacci is slow for large `n` (this is what leads later to **memoization/dynamic programming**, which stores answers instead of recalculating them — you'll meet this properly in Phase 12).

---

## 7. Recursion Tree (Visualizing Recursion)

A recursion tree is just a diagram of every function call, drawn as a tree, where:
- Each node = one function call
- Children of a node = the recursive call(s) made inside that call
- Leaves (bottom of the tree) = base case calls, where recursion stops

Drawing this out by hand for tricky problems is one of the best habits you can build — it makes the "waiting" behavior and the total number of calls visually obvious.

## 8. Iterative vs Recursive — Side by Side

```java
// Iterative factorial
int factorialIterative(int n) {
    int result = 1;
    for (int i = 1; i <= n; i++) {
        result *= i;
    }
    return result;
}

// Recursive factorial
int factorialRecursive(int n) {
    if (n == 0) return 1;
    return n * factorialRecursive(n - 1);
}
```

| | Iterative | Recursive |
|---|---|---|
| Uses a loop? | Yes | No — calls itself instead |
| Uses extra memory (call stack)? | No | Yes — one stack frame per call |
| Risk of Stack Overflow? | No | Yes, if base case is missing/unreachable or input is very large |
| Often easier to read for... | Simple repeated actions | Problems that naturally break into smaller versions of themselves (trees, backtracking, divide & conquer) |

## 9. Common Mistakes People Make

- Forgetting the base case entirely.
- Writing a base case that's never actually reached (e.g., checking `n == 0` but the recursive call does `n - 2`, so it might skip past 0 to negative numbers).
- Thinking recursion "runs faster" than loops — it doesn't; it often uses more memory due to the call stack, and can be slower due to repeated work (like in plain Fibonacci).
- Not tracing through an example by hand before coding — this is the single best habit for actually understanding recursion instead of memorizing syntax.

## 10. Full Interview Q&A

**Q1: What are the two essential parts of every recursive function?**
A: A base case (stopping condition, returns directly without recursing) and a recursive case (calls itself with a smaller/simpler input, moving toward the base case).

**Q2: What is the call stack, and why does it matter for recursion?**
A: The call stack is where Java stores information about each active function call (its local variables and where to resume after it finishes). Every recursive call adds a new frame to this stack, and each call "waits" — paused — until the call it made finishes and returns a value.

**Q3: What is a StackOverflowError, and what causes it?**
A: An error thrown when the call stack runs out of memory, usually because a recursive function calls itself endlessly without reaching a base case (missing base case, unreachable base case, or extremely deep recursion).

**Q4: Why does `factorial(4)` have to "wait" for `factorial(3)`?**
A: Because `factorial(4)`'s final answer depends on multiplying `4` by whatever `factorial(3)` returns — it literally cannot compute its own answer until the call it made gives one back. This pause-and-wait chain continues down to the base case, then unwinds back up.

**Q5: Why is plain recursive Fibonacci considered inefficient for large inputs?**
A: Because it recalculates the same smaller subproblems repeatedly (e.g., `fib(2)` gets computed multiple times within the tree), leading to exponential time complexity instead of reusing already-computed answers.

**Q6: What's the difference between an iterative and a recursive solution in terms of memory?**
A: Iterative solutions typically use constant extra memory (just a loop variable). Recursive solutions use additional memory proportional to the depth of recursion, since each call adds a frame to the call stack.

**Q7: How do you avoid stack overflow when writing recursive functions?**
A: Always confirm there's a base case, and confirm that every recursive call moves the input closer to that base case (never further away or stuck in place).

**Q8: What is a recursion tree used for?**
A: Visualizing every function call as a tree structure, to understand how many calls are made, which calls repeat unnecessary work, and how deep the recursion goes.

## 11. One-Minute Summary (say this out loud before an interview)

"Recursion is a function calling itself to solve smaller versions of the same problem, always needing a base case to stop and a recursive case that moves toward it. Each call is stored as a frame on the call stack and pauses — waiting — until the call it made returns a value, then resumes and completes its own computation. If the base case is missing or unreachable, calls pile up endlessly and the stack runs out of memory, causing a StackOverflowError."
