# Scanner & BufferedReader — Complete Interview Prep Notes

---

## 1. What is Scanner? (Simplest Explanation)

`Scanner` is Java's beginner-friendly way to read input — from the keyboard (`System.in`), a file, or even a String. Think of it like a helper that reads input and automatically converts it into whatever type you ask for (int, String, double, etc.).

```java
import java.util.Scanner;

Scanner sc = new Scanner(System.in);
int n = sc.nextInt();          // reads one integer
String name = sc.next();       // reads one word (stops at whitespace)
String line = sc.nextLine();   // reads the whole line, including spaces
```

**Why it's popular:** it's simple and handles type conversion for you — you don't need to manually parse strings into numbers.

---

## 2. What is BufferedReader? (Simplest Explanation)

`BufferedReader` reads raw text, line by line, as fast as possible — no automatic type conversion, no fuss. It "buffers" (stores a chunk of) input in memory first, which is why it's much faster than reading character-by-character.

```java
import java.io.BufferedReader;
import java.io.InputStreamReader;
import java.io.IOException;

BufferedReader br = new BufferedReader(new InputStreamReader(System.in));
String line = br.readLine();               // reads one full line as a String
int n = Integer.parseInt(br.readLine());   // you convert types yourself
```

**Why it's faster:** `Scanner` re-parses input token by token using regex internally, which adds overhead. `BufferedReader` just reads raw lines — no regex, no type-checking — so on large inputs (think: competitive programming, big test cases) it's noticeably quicker.

## 3. Core Scanner Methods (with Why/How)

```java
Scanner sc = new Scanner(System.in);

sc.nextInt();       // reads next int
sc.nextLong();      // reads next long
sc.nextDouble();    // reads next double
sc.next();          // reads next word (stops at space/newline)
sc.nextLine();      // reads the rest of the current line (including spaces)

sc.hasNext();       // true if there's more input to read — useful for loops
sc.hasNextInt();    // true if the next token is a valid int

sc.close();         // closes the scanner — always do this when done
```

**Classic gotcha:** calling `nextInt()` then `nextLine()` right after — `nextInt()` doesn't consume the newline character left behind, so the following `nextLine()` reads an empty string instead of what you expect. Fix: add an extra `sc.nextLine();` after `nextInt()` to "eat" that leftover newline, or just use `nextLine()` everywhere and parse manually.

## 4. Core BufferedReader Methods

```java
BufferedReader br = new BufferedReader(new InputStreamReader(System.in));

br.readLine();      // reads one line as a String, or null if input has ended
br.read();          // reads a single character (returns an int)
br.close();         // closes the reader — always do this when done

// Reading multiple values on one line, split by space
String[] parts = br.readLine().split(" ");
int a = Integer.parseInt(parts[0]);
int b = Integer.parseInt(parts[1]);

// Reading n lines in a loop
int n = Integer.parseInt(br.readLine());
for (int i = 0; i < n; i++) {
    String line = br.readLine();
}
```

**Note:** `BufferedReader` throws a checked `IOException`, so any method using it must either `throws IOException` or wrap the calls in a `try-catch`.

---

## 5. The Classic Use Case: Reading Competitive Programming / DSA Input

This is the pattern you'll use constantly when solving problems that take input from stdin (GeeksforGeeks, Codeforces-style judges, etc.) — reading a count, then that many values.

```java
BufferedReader br = new BufferedReader(new InputStreamReader(System.in));
int n = Integer.parseInt(br.readLine().trim());
int[] arr = new int[n];

StringTokenizer st = new StringTokenizer(br.readLine());
for (int i = 0; i < n; i++) {
    arr[i] = Integer.parseInt(st.nextToken());
}
```

**Why `StringTokenizer` often replaces `.split(" ")` here:** `split()` uses regex under the hood, which is slower on large inputs. `StringTokenizer` is a lighter, faster way to break a line into tokens when performance matters (large test cases, timed judges).

## 6. Scanner vs BufferedReader — Side by Side

| | Scanner | BufferedReader |
|---|---|---|
| Speed | Slower (uses regex parsing) | Faster (raw buffered reads) |
| Type conversion | Automatic (`nextInt()`, `nextDouble()`, etc.) | Manual (`Integer.parseInt()`, etc.) |
| Ease of use | Beginner-friendly | Slightly more setup |
| Exception handling | None required | Must handle/throw `IOException` |
| Best for | Small inputs, simple programs, learning | Large inputs, competitive programming, performance-sensitive code |

---

## 7. Common Mistakes People Make

- Mixing `nextInt()`/`nextDouble()` with `nextLine()` on `Scanner` without accounting for the leftover newline — causes the next `nextLine()` to silently return an empty string.
- Forgetting `BufferedReader.readLine()` needs to be wrapped in a try-catch or the method needs `throws IOException` — this trips people up the first time they switch from `Scanner`.
- Using `Scanner` for large competitive programming inputs and getting a Time Limit Exceeded (TLE) verdict purely due to slow I/O, not a wrong algorithm.
- Forgetting to `.trim()` a line read by `BufferedReader` before parsing it — trailing spaces/newline characters can cause `NumberFormatException` when converting to int.
- Not closing `Scanner`/`BufferedReader` after use, which can leak resources in larger programs (not critical for short DSA scripts, but a bad habit).

## 8. Full Interview Q&A

**Q1: What's the main difference between Scanner and BufferedReader?**
A: `Scanner` is simpler and does automatic type conversion (`nextInt()`, `nextDouble()`) but is slower because it parses input using regex. `BufferedReader` only reads raw text lines, is faster because it buffers input, but requires you to manually convert types and handle `IOException`.

**Q2: Why would you choose BufferedReader over Scanner in competitive programming?**
A: Performance. `BufferedReader` reads input significantly faster on large datasets since it avoids the regex-based token parsing that `Scanner` does internally — this matters when a judge has strict time limits.

**Q3: Why does calling `nextInt()` followed by `nextLine()` cause a bug?**
A: `nextInt()` only consumes the integer itself, leaving the newline character (`\n`) after it in the input buffer. The very next `nextLine()` call then reads that leftover newline as an empty line instead of the next actual line of input.

**Q4: Does BufferedReader require exception handling? Why?**
A: Yes — `readLine()` throws a checked `IOException`, since reading from an input stream can fail (e.g. the stream is closed unexpectedly). Java forces you to either catch it or declare `throws IOException` on the method.

**Q5: How do you read multiple space-separated integers from one line efficiently?**
A: Read the line with `BufferedReader.readLine()`, then split it — using `StringTokenizer` for better performance on large inputs, or `String.split(" ")` for simplicity — and convert each token with `Integer.parseInt()`.

**Q6: What does Scanner's `hasNext()` method do, and when is it useful?**
A: It returns `true` if there's more input available to read, `false` otherwise. It's commonly used to read an unknown number of inputs in a loop, e.g. `while (sc.hasNextInt()) { ... }`.

**Q7: What happens if BufferedReader.readLine() reaches the end of input?**
A: It returns `null`. This is commonly checked in a loop condition, e.g. `while ((line = br.readLine()) != null) { ... }`, to read until input ends.
